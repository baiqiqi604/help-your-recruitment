# 简历案例库（resume_kb）设计方案

> **状态**：📋 待实现（想法留存，2026-08-18 立项）
> **目标**：把每次定制化生成的简历存入 RAG 案例库，后续遇到相似 JD 需求时直接召回历史结果，跳过 LLM 生成，节省 token 与耗时。
> **适用范围**：`langgraph_version`（主力）与 `langchain_version`（并行开发版）双版本同步落地。

---

## 1. 背景与目标

当前每次简历优化都完整走 LLM 流水线（`analyze_jd → research_company → optimize → review → interview → write_output`），即使新 JD 与历史处理过的岗位高度相似，也会重新调用大模型生成一遍，成本高、耗时长。

**目标**：将「JD 特征 + 生成简历」沉淀为可检索的案例库，新请求命中相似案例时直接复用历史产物，免于 LLM 生成。

**收益**：
- 相似 JD 请求秒级返回、零 token 消耗；
- 简历沉淀为私有案例资产，越用越准；
- 未命中时仍走原流程，命中判定失败可优雅回退，不影响主流程。

## 2. 总体思路

复用现有 ChromaDB 基建（BGE embedding、标题索引→全文映射→Rerank 精排，与 `jd_knowledge_base.py` / `interview_knowledge_base.py` 同一套模式），新增「简历案例库」集合：

```
新 JD 请求
  → ① 检索 resume_kb_title（短文本索引，召回准）
  → ② 按 id 映射回 resume_kb_fulltext（完整 JD + 简历）
  → ③ Rerank 精排 + 相似度阈值判定
  → 命中? → 直接复用缓存简历（from_cache=True，跳过 optimize/review）
  → 未命中 → 原 LLM 流水线 → 生成成功后 upsert 入库（积累）
```

## 3. 存储设计

### 3.1 新增文件

新建 `resume_knowledge_base.py`（仿 `jd_knowledge_base.py`，复用其 `BGEEmbeddingFunction` / ChromaDB 客户端 / `rerank()`）。

### 3.2 config.py 扩展

```python
# 简历案例库（resume_kb）—— 相似 JD 免 LLM 召回
CHROMA_CONFIG["collection_resume_fulltext"] = "resume_kb_fulltext"
CHROMA_CONFIG["collection_resume_title"]   = "resume_kb_title"

RESUME_CACHE_CONFIG = {
    "enabled": os.getenv("RESUME_CACHE_ENABLED", "1") != "0",  # 总开关，0 完全回退现状
    "min_score": float(os.getenv("RESUME_CACHE_MIN_SCORE", "0.82")),  # 命中阈值（Rerank 分数）
}
```

### 3.3 单条记录结构（沿用现有双集合模式）

| 层 | 内容 | 说明 |
|---|---|---|
| 标题索引（检索单元） | `岗位：{role_position}\n公司：{company}\n技能：{required_skills}\n职责：{responsibilities 摘要}` | 短文本，短查询对短文档距离更低，召回更准 |
| 全文（取回） | 完整 JD + 优化后简历全文（`optimized_text`） | 命中后返回的最终产物 |
| metadata | `company` / `role_position` / `required_skills`(逗号串) / `review_pass` / `resume_docx_path` / `resume_html_path` / `created_at` / `source` | ChromaDB 只支持标量值 |

**关键设计**：
- **id 幂等**：`md5(jd_text)`（或 公司+岗位+技能 hash）作为 doc id，同一 JD 再次优化时 `upsert` 覆盖，天然去重；
- **质量把关**：只入库 `review` 审核通过的简历（`review_pass=True`），保证案例质量；
- **标题索引**：id 带 `#t` 后缀（与 `jd_knowledge_base._TITLE_ID_SUFFIX` 一致），检索后还原为正式 id 并映射回全文。

## 4. 检索与命中判定

仿 `search_jds` 链路：

1. query 用 `jd_text`（或 `jd_analysis` 的 `role_position` + `required_skills` 拼接）；
2. 查 `resume_kb_title` → 命中后按 id 映射回 `resume_kb_fulltext` 取回完整内容；
3. `rerank()` 精排，取 top_k；
4. **命中条件**：Rerank 分数 ≥ `RESUME_CACHE_CONFIG["min_score"]`（默认 0.82，可调），且 `review_pass=True`；不满足即视为未命中，回退 LLM；
5. **优雅降级**：缺 chromadb / embedding 依赖时返回空列表（与 `search_jds` 一致），不影响主流程。

## 5. 图流程接入（graph.py）

在 `optimize` 节点前插入查询节点 + 条件路由：

```
load_resume → analyze_jd → research_company → resume_cache_lookup
    ├─ 命中 → review（或直接）→ interview → write_output（optimized_text 直接用缓存）
    └─ 未命中 → optimize → review → …（原流程）
```

- 新节点 `resume_cache_lookup`：检索命中则把 `optimized_text` / `resume_docx_path` / `resume_html_path` / `resume_yaml_path` 等写入 state，并置 `from_cache=True`；
- 条件路由 `route_after_cache`：命中 → 跳过 `optimize`（直接走 review/interview/write_output）；未命中 → `optimize`；
- 命中路径**不再调用 LLM**（省 token + 提速）；
- `OptimizeState` 增加字段：`from_cache: bool`（默认 False）。

## 6. 写入时机

`write_output` 成功产出后（review pass 且文档生成完成），把本次「JD 特征 + optimized_text + 文档路径」upsert 入库；失败仅记 warning（与 `add_experiences` 模式一致），不影响主流程。

## 7. Web / API 改造

- `/api/optimize` 返回值增加 `"from_cache": true/false`；
- 前端"定制化结果"展示命中提示：`✅ 已命中历史相似案例（免 LLM 生成）`；
- 可选管理接口：
  - `GET /api/resume-kb/stats`：案例库总数；
  - `GET /api/resume-kb/search?q=`：调试检索。

## 9. 关键取舍与风险

| 项 | 说明 |
|---|---|
| 命中误判风险 | 命中简历与当前 JD 匹配不足 → 用**阈值 + review 双把关**兜底 |
| 多用户隔离 | 当前单人场景无需；若有多用户需按用户 id 过滤（metadata 加 `user_id` + `where` 过滤） |
| 隐私 | 简历属敏感数据，案例库存本地 ChromaDB，无外传；如需清理提供 `clear_resume_kb()` 接口 |
| 开关 | `RESUME_CACHE_ENABLED=0` 可随时关闭，行为完全回退现状 |
